# 面试问答准备 · 智能简历筛选系统

> 用法：先通读，理解每条"为什么"；面试前只复习每题的**加粗关键词**。
> 项目整体介绍见 [project-brief.md](project-brief.md)。

---

## A. 项目整体

**A1. 一句话介绍这个项目**

> 一个智能简历筛选系统：HR 上传简历、写一句话岗位需求，系统自动完成解析、语义召回、硬性过滤、六维加权评分，并对排名靠前的候选人生成评估报告。我独立设计并实现了后端全部链路，包含异步任务、幂等、评分模型和 448 个自动化测试。

**A2. 你在项目里具体做了什么？**

参考了开源项目 LLM-Agent-Resume 的产品思路，**底层重写**。主要工作：把业务编排从接口层下沉到服务层；把内存 + 向量库两套真源合并成数据库唯一真源；引入异步任务队列与业务幂等；把权重策略外置成配置并做启动校验；补齐分层测试与端到端验收。

**A3. 项目规模？**

约 5400 行 Python，11 张表，10 个 HTTP 接口，3 套评分档案，3 个带版本号的提示词模板，448 个测试用例（6–9 秒跑完）。

**A4. 最大的难点是什么？**

不是调大模型，是**在引入异步之后仍然保证结果正确**。队列只能保证"至少执行一次"，所以上传去重、重复入库、重复提交筛选都必须能扛住重复执行；同时删除简历时还要让旧的筛选结果自动失效。这三件事共同构成了系统的一致性边界。

**A5. 如果重做，你会改什么？**

会把"地点匹配"和"技能同义词"从我写的启发式规则换成词表 + 别名映射；会把鉴权从第一天就设计进去，而不是等上线前补；测试里再加一层针对真实模型输出的回归样本。

## B. 架构与分层

**B1. 为什么分五层？会不会过度设计？**

分层的目的是**隔离变化**：界面会变、模型会换、数据库会迁，但"本科学历够不够"这条规则不会变。所以把最稳定的业务规则放在最底层且不依赖任何框架，把最容易变的技术细节放到最外层。

**不过度**，因为每层都有实际的替换需求：大模型换供应商、向量库从 sqlite-vec 扩到 Milvus、存储换 PostgreSQL——这三种替换在项目周期内都是可预期的。

**B2. domain 层零依赖怎么保证？**

约定 + 代码审查。`domain/` 里只 import 标准库（`re`、`datetime`、`dataclasses`），不 import `fastapi`、`openai`、`sqlite3` 或任何 adapter。验证方式是一条命令：`grep -rn "fastapi\|openai\|sqlite3" app/domain/` 应返回空。

严格说这不是编译器强制的，但可以通过 CI 的 import linter 变成硬约束——这是我下一步想加的。

**B3. 端口为什么用 Protocol 而不是抽象基类？**

`Protocol` 是结构化类型：实现类不需要显式继承，只要方法签名对得上就满足契约。好处是 adapter 不需要 import port（减少耦合），测试里的假实现也能随手写一个类。

**代价**：少了运行时的接口校验，漏实现方法只能等到调用时才报错。抽象基类（ABC）能强制实现全部方法，但会让 adapter 必须继承，且测试替身必须写全所有方法。

**B4. services 和 api 的边界怎么划？**

`api/` 只做四件事：收参数、校验、调用服务、序列化返回。它**不决定流程顺序**。

判断标准很简单：如果换个入口（CLI、定时任务、消息队列）也要执行同样的步骤，这段逻辑就必须在 `services/`。比如"上传后要解析、抽取、建索引"这个顺序，跟 HTTP 毫无关系。

**B5. 组合根是什么？为什么要它？**

组合根是**唯一允许把接口和实现连在一起的地方**。这个项目里有两处：Web 进程的 `create_app()` / `get_context()`，和 Worker 进程的 `build_worker()`。

好处有两个：一是换实现只改装配代码，业务代码不动；二是 import 阶段不读配置、不连数据库，缺少 API Key 时服务能正常导入，只在第一个请求时报错——这让测试可以只 import 而不启动服务。

**B6. 为什么拆成 Web 进程和 Worker 进程？**

Web 进程只做毫秒级的事（校验、落盘、入队、读结果），Worker 负责十几秒的重活（解析、调模型、嵌入）。

拆开的好处：Web 再忙也不影响任务处理；Worker 崩了重启即可，任务不会丢；两者可以独立扩容。代价是部署多一个进程，用启动脚本解决。

**B7. 换一个大模型 / 向量库要改哪里？**

大模型：实现 `LLMPort`（两个方法：结构化抽取、自由生成），然后在组合根里换掉构造那行。因为走 OpenAI 兼容协议，换供应商通常只改配置。

向量库：实现 `VectorStorePort`（写入、检索、删除、重建），同样是改装配行。接口只暴露相似度 `[0,1]`，不暴露距离，避免不同向量库的距离语义不一致。

**B8. 如果让你加"同一人多份简历合并"，从哪下手？**

三处：`domain/` 加合并规则（按姓名 + 手机号 + 邮箱判断是否同一人）；`services/ingestion.py` 在抽取完成后调用规则，合并到一条主记录、其余标记为副本；数据库加一张关联表记录主从关系。

**关键**：合并规则必须放在 domain，因为它需要单测，而且未来可能调整。

## C. 数据与一致性

**C1. 为什么用 SQLite？**

单机场景零运维、事务完整、文件即数据库，演示和中小规模完全够用。选它还有一个原因：**它能同时承载业务数据和任务队列**，不需要额外引入 Redis。

风险我也清楚：单写者模型，并发写入会排队。缓解手段是 WAL 模式 + 5 秒 busy timeout。规模上去后迁 PostgreSQL，仓储层已经是接口，改实现即可。

**C2. WAL 模式解决什么问题？**

默认的日志模式下，读和写会互相阻塞。WAL（预写日志）让**读不阻塞写、写不阻塞读**，只有写和写之间需要排队。对"Web 进程频繁读、Worker 进程频繁写"这个场景很关键。

代价是多了 `-wal` 和 `-shm` 两个文件，且不能放在网络文件系统上。

**C3. 什么是"唯一真源"？**

数据库里的业务数据是唯一事实来源。向量索引、缓存、Excel 导出这些都是**派生数据**——丢了可以由真源重新生成。

具体体现：向量存在独立的索引文件里，删除简历时同时删记录、原始文件、向量；索引损坏时直接重建，不影响业务数据。

**C4. 幂等键怎么设计的？**

`sha256(岗位文本 + 评分档案 + 简历库版本)`。

三个因子各有作用：岗位文本决定"筛什么人"；档案决定"用什么权重"；**简历库版本最关键**——新简历入库后版本号 +1，旧的筛选结果自动失效，否则新候选人永远不会出现在历史结果里，而 HR 看不出任何异常。

**C5. 那如果只改了权重配置、简历库没变呢？**

**会命中旧结果——这是已知缺陷。** 结果表里其实已经存了配置快照，只是没把配置指纹放进幂等键。

修法很简单：配置指纹进 key。我没改是因为它会让每次调参都强制重算，演示时反而不方便；但它确实应该在上生产前修掉。

**C6. 删除简历时发生了什么？**

四件事必须一起做：删业务记录（含关联的技能、地点、学历、经历行）、删原始 PDF 文件、删向量索引、递增简历库版本号。

**最容易漏的是第四件**：不递增版本号，删除前算出的结果会一直有效，里面还带着这个人的信息。

**清空简历库时还要多清一样：队列任务。** 否则已经排队的"解析简历"任务会在简历被删后又把它重建出来。

**C7. 内容哈希去重会不会误伤？**

不会。哈希是对**完整文件字节**算的：同一份文件必然同哈希，不同内容必然不同哈希（SHA-256 碰撞概率可忽略）。

它解决的是"同一份 PDF 重复上传"，不解决"同一个人不同版本的简历"——后者需要姓名/手机号/邮箱层面的合并规则，目前没做。

**C8. 数据库怎么做迁移？**

目前没有迁移机制，建表语句全部是 `IF NOT EXISTS`，只能向前兼容地加表。

上生产前应该引入简单的版本表 + 顺序迁移脚本（或直接用 Alembic）。这是我在局限清单里明确列出的 P2 项。

## D. 异步任务与并发

**D1. 为什么要异步？**

解析 PDF、调大模型抽取、生成嵌入，一份简历要 8–15 秒。同步放在 HTTP 请求里，用户要等、连接会超时、并发能力几乎为零。

异步之后，上传接口是毫秒级返回，用户刷新页面看到状态从"排队"变成"已入库"。

**D2. 为什么不用 Celery + Redis？**

当前规模下，引入 Redis 意味着多一个必须部署、必须监控、必须备份的组件，而它能带来的并发优势用不上。

SQLite 队列的语义（锁定、重试、死信）是我自己实现的，**行为完全可控，也便于讲清楚**。接口已经抽象成 `TaskQueuePort`，真要换 Celery 只需要实现同一个端口。

**面试加分点**：这不是"不会用"，是"当前规模不需要"。

**D3. 可见性锁是什么？**

领取任务时**不删除任务**，而是把"锁到期时间"推到 60 秒后，同时把尝试次数 +1。任务完成后才真正删除。

如果 Worker 在处理中崩溃，锁到期后任务自动变回可领取状态——这是崩溃恢复的基础。如果处理完成却来不及确认，任务会被别人再处理一次，所以业务必须幂等。

**D4. 为什么尝试次数在"领取时"加，而不是"失败时"加？**

因为要覆盖"领取后直接崩溃、根本没机会报告失败"的情况。如果只在失败时计数，这类任务会被无限重试。

**D5. Worker 崩溃了任务会丢吗？**

不会。任务在数据库里，锁 60 秒后自然过期。重启 Worker 就会重新领取。

**会重复**，所以靠三层幂等兜底：已入库的简历直接返回、已完成的筛选直接返回、上传按内容哈希去重。

**D6. 多个 Worker 会不会重复处理同一条任务？**

不会。领取是一条**原子 UPDATE**：在一个事务里用子查询挑出"待处理且锁已过期"的任务，同时把它锁住并返回。两个 Worker 并发领取，只有一个能拿到。

代价是这条 UPDATE 会短暂持有写锁，所以并发量大的时候要考虑换专业队列。

**D7. 死信是什么？**

重试到上限（默认 3 次）或遇到**永久性错误**的任务，状态改成 `dead`，不再被领取，但保留在表里供排查。

永久性错误包括：文件解析失败（重试一万次也一样）、参数缺失、类型错误。而模型调用失败、嵌入失败算临时错误，值得重试。

**D8. SQLite 写锁会不会是瓶颈？**

会。SQLite 同时只允许一个写者。当前缓解手段是 WAL（读写不互斥）+ 5 秒 busy timeout，演示和几十并发没问题。

瓶颈点会先出现在任务队列的并发领取上。扩展路径明确：数据库换 PostgreSQL、队列换 Redis 或专业消息队列，业务代码不用动。

## E. 检索与评分

**E1. 为什么先召回再过滤？**

召回只看文本像不像，**不依赖任何字段抽取质量**；过滤依赖学历、经验、地点这些抽取结果，而抽取会出错（英文 Bachelor 没识别、日期格式异常、Beijing 对不上北京）。

先过滤的话，一次抽取失误就是永久出局，而且**无声无息**——那个人根本不会出现在结果里。先召回至少能让"内容明显匹配但字段没抽好"的人进候选池，再用未知字段策略兜底。

**E2. 那先召回不是会漏掉"语义排名靠后但硬条件完美"的人吗？**

会，这是真实代价。`top_k` 截断发生在过滤之前，最终合格人数大约是 `top_k × 通过率`。

缓解办法是**放大候选池**：默认档案召回 100 条，严招档案放宽到 200 条。如果通过率 30%，想要 100 个合格候选人，`top_k` 就得开到 300 以上。

**E3. 为什么不用向量库的元数据过滤？**

两个原因。一是参考项目把技能列表序列化成 JSON 字符串塞进向量元数据，导致无法做原生过滤——我把技能、地点、学历、经历拆成了独立的关系表并建索引。二是结构化查询交给 SQL 更可控（能解释执行计划、能加联合索引），向量库只做它最擅长的相似度计算。

**E4. 六维权重凭什么这么定？**

这是业务策略，不是技术判断，所以我没有写死在代码里——放到配置文件，提供三套档案：技术岗（技能 40%）、销售岗（行业 30%）、严招（缺失字段直接淘汰）。

**如果被追问"40% 的依据"**：坦白说这是初始经验值，正确做法是用历史招聘结果做回归或让 HR 调参。系统已经提供了配置和接口，缺的是真实数据来标定。

**E5. 缺失字段为什么剔除分母？**

如果没写薪资就按 0 分算，分数反映的是"简历写得多全"，不是"人有多匹配"。剔除分母后，只有有数据的维度参与加权，同时输出"覆盖率"告诉使用者这次评分覆盖了几维。

**代价**：岗位只写两三个条件时，合格者容易拿到 0.9 以上，区分度下降。所以覆盖率必须一起展示。

**E6. 语义分为什么是混合，而不是第七个维度？**

因为语义分的量纲和"六维"不同：六维是规则算出来的匹配度，语义分是整体相似度，两者不在一个尺度上。

混合方式：`最终分 = 六维加权分 × (1 - w) + 语义分 × w`，`w` 默认 0.2。这样语义分扮演"微调"角色，不至于压过硬规则。

**E7. 为什么每个维度返回分数 + 权重 + 理由？**

为了可解释。HR 看到"技能 0.6，权重 40%，理由：命中 Python/Redis，未命中 K8s"才能判断这个分数是否可信。

参考项目只返回一个总分，导致它只能在接口层**伪造**单项分——因为领域层根本没把过程信息带出来。

**E8. 怎么评估召回质量？**

目前只做了端到端验收，没有量化指标。正确做法是准备一个标注集（岗位 + 人工认定的合格候选人），计算召回率与排序质量（如 NDCG）。

这是这个项目在"AI 工程"层面最欠缺的一环，面试时应该主动承认。

## F. 大模型应用

**F1. 怎么保证模型输出格式稳定？**

四层：提示词里明确"只输出 JSON、不要代码块"；把 Pydantic 模型的 JSON Schema 嵌进提示词；使用 JSON 模式强制返回合法 JSON；返回后用 Pydantic 校验，失败则重试（默认最多 3 次）。

**为什么不用 tool calling**：DeepSeek 的 tool calling 支持面较窄，JSON 模式更稳。两者本质等价，都是"用 schema 约束输出"。

**F2. 幻觉怎么处理？**

三个层面：

- **输入约束**：提示词要求只能从简历原文抽取，不得推测。
- **输出校验**：所有字段经过结构化模型校验，类型和枚举值不对直接重试。
- **下游兜底**：报告只基于已抽取的结构化字段生成；关键字段保留原文，供人工核对。

**必须承认**：做不到完全消除。所以系统定位是"辅助筛选"，不是"自动录用"。

**F3. 为什么提示词要带版本号？**

因为提示词是**和代码同等级的策略**。改了提示词，抽取质量就变了。带版本号并落库，将来发现某一批简历抽得差，能定位到当时用的是哪一版。

升级方式是新建 `.v2.txt`，不原地改——否则历史结果无法复现。

**F4. 为什么要注入当前日期？**

模型没有"今天"这个概念，只能用训练数据里的时间。曾经出现过报告判定"候选人工作时间晚于当前时间、疑似造假"，实际原文是 `2025.08–2026.09`，而当时是 2026 年 10 月——那只是上个月。

修法是在**系统提示词里统一注入日期锚点**，而不是每个模板各写一遍；同时约束抽取器对"至今"原样返回，不在写入时换算成具体月份。

**F5. 成本怎么控制？**

四条：只对前 10 名生成报告（最贵的一步）；同一输入命中幂等，不重复调用；抽取阶段用结构化输出减少重试；嵌入用本地模型，零调用费用。

**F6. 模型服务挂了怎么办？**

临时性失败（连接错误、限流、5xx）自动重试，SDK 层和业务层各有一层；重试到上限进死信，保留错误信息。任务本身不丢，恢复服务后可以重放。

**目前缺的是告警**——死信只能靠翻表发现。

**F7. 为什么 temperature 设 0？**

抽取和评分要的是稳定复现，不是创造力。同一份简历今天抽出来是"本科"，明天不能变成"硕士"。

## G. API 设计

**G1. 为什么 POST 返回 202 而不是 200？**

202 的语义是"已接受，处理中"。任务还没完成，返回 200 会误导调用方以为结果已经就绪。响应里直接给出 `run_id`，调用方拿它轮询进度。

**G2. 为什么强调 GET 不能有副作用？**

因为浏览器、代理、爬虫都可能重复发 GET。参考项目的查询接口每次调用都会重跑全流程、重新调 N 次大模型——刷新一次页面就烧一次钱，而且结果可能每次不同。

这个项目里，查询接口是纯读，重算只发生在 POST。

**G3. 分页参数怎么校验？**

用框架的参数校验：`limit` 限制在 1–100，`offset` 不小于 0，越界自动返回 422。业务代码里不需要再写判断。

**G4. 为什么没有鉴权？**

客观原因是当前定位是本地演示，用户只有一个。**但这是上生产前的第一优先级**：简历是个人隐私数据，现在等于裸奔。

补法是 API Key 或 JWT，并且清空、删除这类管理接口要单独授权。

**G5. 清空简历库为什么要连队列一起清？**

因为已排队的"解析简历"任务持有 `resume_id`。如果只删简历不删任务，任务执行时会发现记录不存在，然后**重新创建一条**——清空等于没清。这是个典型的"异步系统里的级联删除"问题。

## H. 测试与质量

**H1. 448 个测试怎么组织的？**

三层：单元测试（日期归一、经验时长、六维打分、硬过滤、配置校验）、适配器测试（数据库、队列锁与重试、PDF 解析、向量检索）、接口测试（上传、列表、详情、提交筛选、读结果、清空）。

**H2. 怎么做到不调用真实模型？**

依赖注入。服务和适配器的构造函数都接收接口类型，测试里传入假实现：假 LLM 返回固定结构化数据、假嵌入返回确定性向量、数据库用临时文件。

**H3. 为什么 9 秒能跑完？**

业务规则是纯函数，没有 IO；适配器测试用内存或临时 SQLite；接口测试用进程内测试客户端，不起服务器；没有任何网络调用。

**H4. 有没有端到端测试？**

有，是脚本形式的验收：真实启动服务、上传真实 PDF、真实调用模型、轮询到完成、校验结果。它不放进常规测试套件，因为它慢、要花钱、依赖外部服务。

**分层原则**：单元测试保证逻辑正确，验收脚本保证链路正确，两者不能互相替代。

## I. 运维与扩展

**I1. 怎么部署？**

开发/演示用一条启动脚本，同时拉起 Web 和 Worker。生产建议两个进程分开部署、独立扩容，前面放反向代理。

**I2. 出问题怎么排查？**

三个入口：简历状态和失败原因在数据库里（哪一步失败一目了然）；任务表有尝试次数和最后一次错误；Worker 日志按任务 id 记录全过程。

**I3. 1000 人同时上传会怎样？**

会先卡在 SQLite 的写锁上。缓解顺序：上传接口做限流、任务队列换 Redis、数据库换 PostgreSQL。架构上不需要改业务代码，因为仓储和队列都是接口。

**I4. 简历到 10 万份怎么办？**

数据库迁 PostgreSQL，向量索引迁 Milvus，任务队列换专业组件，Worker 横向扩展。另外需要重新评估 `top_k`——10 万份里取 100 条，召回率会明显下降，需要分层召回（先按城市/行业预筛）或增加索引类型。

## J. 反思类

**J1. 这个项目最大的不足？**

**没有量化评估**。我做了端到端验收，但没有标注集去算召回率和排序质量。一个 AI 应用如果只能说"跑通了"，不能说"效果多好"，是不完整的。

**J2. 你从中学到什么？**

三件事：一是**幂等不是可选项**，只要有异步就必须考虑重复执行；二是**可解释性要设计出来，不是事后补**——评分结果带理由，是因为领域层一开始就把过程信息带出来了；三是**AI 应用的成本和确定性，往往比模型能力更决定产品能不能用**。

**J3. 为什么不做成 Agent？**

这个流程五步固定、输入是一句话、工具就五个，Agent 的自主决策没有发挥空间，反而会牺牲结果的可复现性——而可复现是筛选系统的底线。

我保留了确定性管道，只在需求过于模糊时加一次澄清追问。将来如果接入外部人才库、或需要多轮追问才能明确需求，才是引入 Agent 的时机。

**J4. 如果给你一个月继续做？**

按优先级：鉴权（P0）→ 地点与技能的词表归一（P0）→ 标注集与召回评估（P1）→ 报告并发生成（P1）→ Docker + CI + 数据库迁移（P2）→ OCR 支持（P2）。

## 附：三条万能答题结构

1. **被问"为什么这样选"**：先说约束（规模、成本、团队），再说选择，最后说**代价**。只说好处会被追问穿。
2. **被问"有什么问题"**：承认具体缺陷 + 说清影响 + 给出修法。不要答"没有"。
3. **被问"如果量变大"**：把瓶颈按顺序说（数据库写锁 → 队列并发 → 召回质量），每层给出替换方案，并强调**架构上已经留好接口**。
