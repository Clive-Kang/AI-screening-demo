## 一、口播稿（约 700 字，3 分钟）

### 0:00–0:20　这个项目解决什么问题

HR 每天要看大量简历，一份份翻很费时间。这个系统让你把简历传上去、写一句「我要招什么样的人」，剩下的挑人、排序、写评估，全自动完成。

### 0:20–1:10　演示（配合操作）

（启动服务、打开页面）先启动服务。前端是我自己写的一个简单页面，用来做展示，后面还可以再优化。

（拖入三份简历）上传简历，状态会从「排队」变成「已入库」，这一步是后台在处理。

（输入岗位、点「开始筛选」）岗位要求写一句话就行。系统先圈出相关的人，再按学历、经验这些硬条件筛掉不合格的，剩下的打分排序，最后给排名靠前的写评估。

（展开报告）点开能看到每一项的得分和一段总结，写清楚推不推荐、为什么。被淘汰的人也会留着，并写明原因。

### 1:10–2:35　优点

第一，岗位需求只用写一句话，大模型自动拆成学历、技能、经验这些条件，不用填表格。

第二，语义检索和硬性过滤配合：前者找出「像」的人，后者卡住学历、经验这些硬条件，两边互补，不容易漏人。

第三，多维加权评分，权重放在配置文件里，不改代码就能调。

第四，每项分数都带理由，能看懂为什么推荐。

第五，排名靠前的候选人有大模型写的分析报告，直接给结论；也只给前几名写，控制成本。

第六，自带一个开箱即用的网页界面，上传、筛选、看结果都在一个页面里。

第七，向量库和大模型接口都是可插拔的：现在用轻量的 sqlite-vec，以后数据量大了可以换 Milvus；模型接口按 OpenAI 兼容协议写，换供应商基本只改配置。

### 2:35–3:00　还没完善的地方

目前还有三点：一是没有登录和权限，谁都能看到简历，上生产前必须补；二是还没做 Docker 容器化，部署要手动配环境；三是只支持 PDF，Word 和扫描件还处理不了。

（收尾）另外，这套代码有四百多个自动化测试，六秒跑完。

## 二、项目设计思路（不念，用于展开讲解）

### 2.1 分层：依赖只能朝一个方向

```
api ──▶ services ──▶ domain
 │          │          ▲
 └──────▶ ports ◀──────┘
              ▲
          adapters        （只有 main.py / worker.py 在装配时 import）
```

| 层 | 职责 | 禁止 |
|---|---|---|
| `domain/` | 纯规则：怎么算、怎么判 | import 任何框架或 adapter |
| `ports/` | 只写"要什么能力" | 写实现 |
| `adapters/` | SQLite、DeepSeek、Ollama、pdf、队列的实现 | 写业务流程 |
| `services/` | 唯一知道流程顺序的地方 | 直接依赖框架细节 |
| `api/` | HTTP 收参、校验、序列化 | 写业务逻辑 |

**收益**：最难测的评分/过滤规则可以纯函数单测（448 个用例 6 秒跑完）；换 LLM、换向量库只改装配行。

### 2.2 五条核心决策

1. **SQLite 是唯一真源，向量索引是可丢弃的派生数据**
   参考项目简历在内存字典、向量在 Chroma，重启后两边不一致。这里删除简历时同时删真源、向量、原始文件，并 `bump_corpus_version()` 让旧结果失效。

2. **写操作异步化：`POST` 返回 202，`GET` 永远只读**
   参考项目的 `GET /results/{id}` 每次调用都会重跑全流程和 N 次 LLM。这里提交只建 run + 入队，结果落库后 GET 直接读。

3. **任务队列用 SQLite，靠可见性锁而不是"删了就算"**
   `dequeue` 时把 `locked_until` 推到 N 秒后、`attempts + 1`；worker 崩溃后锁过期，任务自动回队。语义是 at-least-once，所以业务侧必须幂等：
   - 重复入库：已 `indexed` 的 `resume_id` 直接返回
   - 重复筛选：已 `succeeded/partial` 的 run 直接返回结果
   - 永久失败（`DocumentParseError`、`ValueError` 等）直接进死信，不浪费重试

4. **策略外置且启动即校验**
   六维权重、召回 top_k、Top-N 都在 `config/scoring.yaml`；权重和必须等于 1.0，否则拒绝启动。**不做静默归一化**——那会让调参的人误以为配置生效了。prompt 带版本号（`*.v1.txt`），落库时记录用了哪个版本。

5. **每个维度返回三元组，而不是一个分数**
   `DimScore(score, weight, reason)`：API 能直接展示"为什么是这个分"，不用像参考项目那样在路由层伪造单项分。

### 2.3 评分模型

```
overall = 六维加权分（缺失维度从分母剔除） × (1 - w) + 语义相似度 × w
```

- 六维：技能、学历、行业、地点、薪资、标签
- 语义分来自向量召回（bge-m3，余弦相似度，只暴露 `similarity ∈ [0,1]`）
- **缺失维度不按 0 分算**：避免"写得越详细分越高"的信息完备性偏差
- **硬过滤与评分分离**：过滤决定"能不能进"，评分决定"排第几"；被淘汰的人仍保留分数和原因

### 2.4 与参考项目相比改掉的 5 个结构性问题

| 参考项目 | 本项目 |
|---|---|
| 业务编排写在 HTTP 路由里，GET 有重副作用 | 编排集中在 `services/`，GET 只读 |
| 内存字典 + Chroma 两套真源 | SQLite 唯一真源，向量可重建 |
| 权重/召回数/prompt 硬编码，文档还互相矛盾 | `scoring.yaml` + 版本化 prompt，启动校验 |
| 导入期单例，缺 key 连 import 都失败 | 组合根 + `Depends` 注入，import 不读配置 |
| 列表被序列化成 JSON 字符串塞进向量元数据 | 结构化拆表（`resume_skills` 等），SQL 下推 |

## 三、当前局限（诚实清单）

按"如果上生产，先修哪个"排序。

| # | 局限 | 影响 | 修法 |
|---|---|---|---|
| 1 | **没有任何鉴权** | 能访问端口的人可以看全部简历、清空库、提交筛选 | 加 API Key / JWT；清空等管理接口单独授权 |
| 2 | **地点匹配是字符串子串**（`score_location`，min_len=2） | `Beijing` 与 `北京`、`上海` 与 `沪` 互不识别，会误杀 | 加地名别名表；或让 LLM 抽取时统一成中文标准城市名 |
| 3 | **幂等键不含配置与 prompt 版本** | 改了 `scoring.yaml` 或 prompt，但简历库没变时会命中旧结果 | key 里加 `config_fingerprint`（已有 `config_snapshot_json`，只是没进 key） |
| 4 | **单个删除不删原始文件**（批量清空会删） | `DELETE /resumes/{id}` 后 `data/blobs/` 里残留 PDF | 删除前取 `blob_path` 并 `unlink` |
| 5 | **Top-N 报告串行生成** | 10 份报告 ≈ 10 倍单次 LLM 延迟 | 用线程池并发，控制在 3–5 并发 |
| 6 | **单 worker 串行消费** | 批量上传 100 份要排队；没有优先级 | 多 worker 进程即可（队列锁已保证不重复），或按任务类型分队列 |
| 7 | **只支持有文字层的 PDF** | 扫描件抽不出文字，任务失败进死信 | 接 OCR（PaddleOCR / 云服务） |
| 8 | **技能/行业匹配是启发式子串** | 无同义词与层级：`k8s` 不命中 `Kubernetes` | 技能词表 + 别名映射；或加一次 LLM 归一 |
| 9 | **缺失维度剔除分母会抬高分数** | 岗位只写 2 个条件时，合格者轻易 0.9+，区分度下降 | 输出 `coverage`（已实现）供前端提示；或按覆盖率做置信度加权 |
| 10 | **死信无管理界面与告警** | 失败任务只能翻 `tasks` 表和日志 | 加 `GET /admin/tasks?status=dead` 与重放接口 |
| 11 | **清空接口一次最多处理 1 万份** | 超过部分清不掉（`list(limit=10_000)`） | 用 `DELETE FROM resumes` 直接批量，或循环直到空 |
| 12 | **无 CI、无容器化、无迁移脚本** | 换机器要手动建环境；schema 变更没有版本管理 | 加 Dockerfile + GitHub Actions + 简单迁移表 |

### 面试时怎么讲局限

不要逐条念。挑 2 条讲，并给出判断：

> 最优先的是鉴权，因为简历是个人隐私数据，现在等于裸奔。其次是地点的中英文归一——这是我在端到端验收时实测发现的：英文简历写 Beijing，岗位写北京，硬过滤直接 0 命中。其余像并发和 OCR 属于规模上来后再处理的问题。

## 四、可能被追问的问题

| 问题 | 一句话回答 |
|---|---|
| 为什么不用 LangChain？ | 流程只有四步且顺序固定，直接写编排更可读、更好测；domain 层也能保持零框架依赖。 |
| 向量库为什么用 sqlite-vec？ | v1 规模小，和真源同库、零运维；接口是 `VectorStorePort`，换 Milvus 只改装配行。 |
| at-least-once 会不会重复扣费？ | 业务侧幂等：已完成的 resume/run 直接短路；文档里也写了"重复投递必须 no-op"。 |
| 权重怎么调？ | `config/scoring.yaml`，和必须为 1.0，否则拒绝启动；改完重启。 |
| 为什么只对 Top-N 生成报告？ | 成本最高的一步；默认 10，可配置。 |
| 系统最大的技术风险？ | SQLite 单写者 + 单 worker；并发上传时队列会成为瓶颈，但 WAL + busy_timeout 已能扛演示规模。 |
