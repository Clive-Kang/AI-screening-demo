# 智能简历筛选系统 · 面试介绍材料

> 用途：面试时介绍这个项目。按面试官给的时间选版本——30 秒版、3 分钟版、展开版。
> **本文只用业务和技术视角描述，不涉及具体代码位置**。需要配合代码讲解时另看 [demo-script.md](demo-script.md)。

---

## 0. 30 秒版

> 这是一个智能简历筛选系统。HR 上传简历、写一句岗位需求，系统自动完成解析、语义召回、硬性过滤、多维评分和报告生成。
>
> 后端是 Python + FastAPI，大模型走 OpenAI 兼容接口，嵌入模型用本地部署的 bge-m3，数据落在 SQLite。现在是 5400 行代码、11 张表、10 个接口、448 个自动化测试。

---

## 1. 1 分钟版

> 这个项目解决的是 HR 筛简历的问题：一百份简历要翻大半天，而且不同人标准不一。
>
> 系统的用法是三步：上传简历、写一句"我要招什么样的人"、看排序和报告。
>
> 技术上核心是一条漏斗：先用向量检索做语义召回，找出"像"的候选人；再用结构化条件卡掉学历、经验、地点不合适的；剩下的做六维加权评分排序；最后只对排名靠前的几个人调用大模型写评估报告。
>
> 我重点做了三件事：一是把写操作全部异步化，上传和提交都立刻返回、后台处理；二是保证任务重复执行也不会算错、不会多花钱；三是把权重、召回数量这些业务策略从代码里挪到配置文件，改策略不用改代码。

## 2. 3 分钟版（四段口述）

### 第一段：业务问题

HR 每天要看大量简历。一份简历认真看两分钟，一百份就是三个多小时，而且筛选标准因人而异、难以复用。更麻烦的是，筛完之后往往还要再花时间给候选人写评价。

这个系统把这件事压缩成三步：上传、写一句话、看结果。

### 第二段：技术方案

后端用 Python 和 FastAPI 写，数据存 SQLite，大模型调用 DeepSeek（走 OpenAI 兼容协议），文本嵌入用本地部署的 bge-m3，向量检索引擎是 SQLite 的向量扩展。

核心是一条五步漏斗：**语义召回 → 硬性过滤 → 多维评分 → 排序 → Top-N 生成报告**。

- 召回负责"找出像的人"，用的是向量相似度；
- 过滤负责"卡住硬条件"，用的是结构化查询；
- 评分负责"排顺序"，用六个维度加权；
- 报告是最后一步，只给前几名调用大模型，控制成本。

### 第三段：架构

代码按职责分成五层：业务规则层、接口定义层、具体实现层、流程编排层、HTTP 接口层。依赖只能单方向走——上层的业务编排依赖下层的业务规则，但业务规则不依赖任何框架、数据库或大模型 SDK。

这样做的直接好处是：**最难测的评分和过滤逻辑可以脱离网络和数据库单独测试**，所以 448 个测试能在几秒内跑完。

### 第四段：我做了什么

原项目是一个能跑通的原型，但结构上有几处硬伤。我主要做了五件事：

1. **业务逻辑从接口层搬进服务层**。原来每次刷新结果页面都会重跑全流程、重新调一遍大模型；现在提交只创建任务，查询只读结果。
2. **合并两份数据真源**。原来简历信息在内存里、向量在另一个数据库，重启后两边对不上；现在数据库是唯一真源，向量只是可重建的索引。
3. **写操作异步化**。引入基于数据库的任务队列，支持失败重试和崩溃恢复，不依赖额外的中间件。
4. **策略外置并做启动校验**。权重、召回数、报告数量都放在配置文件里，权重加起来不等于 1 直接拒绝启动，不做静默修正。
5. **评分结果带过程信息**。每个维度都返回分数、权重和理由，而不是只给一个总分。

## 3. 项目背景

### 3.1 业务痛点

| 痛点 | 具体表现 |
|---|---|
| 耗时 | 单份简历人工阅读约 2 分钟，100 份约 3 小时 |
| 标准不一 | 不同 HR 关注的维度、权重不同，结果不可复现 |
| 只看关键词 | 人工检索容易漏掉"技能名称不同但能力相同"的候选人 |
| 写评价费时 | 通过初筛的候选人还要逐份写推荐理由 |

### 3.2 参考项目与重写动机

整体思路参考了开源项目 **LLM-Agent-Resume**。它验证了"用大模型抽取简历 + 向量检索 + 打分"这条路可行，但作为一个原型，存在几处结构性问题：

| 原项目的问题 | 实际影响 |
|---|---|
| 业务编排写在接口层，查询接口带重副作用 | 刷新结果页会重跑整个流程、重复调用大模型，既慢又费钱 |
| 简历在内存、向量在向量数据库 | 两套真源，进程重启后不一致 |
| 提交后同步等待 | 一次请求要十几秒到几十秒，无法并发 |
| 权重和提示词硬编码 | 调整策略必须改代码；文档里的权重还自相矛盾 |
| 技能、地点被序列化成字符串塞进向量元数据 | 无法做结构化过滤，只能全量取出后内存筛选 |
| 只返回一个总分 | 无法解释"为什么推荐这个人" |

我的工作不是修补，而是保留它的产品思路、重写底层实现。

## 4. 技术栈与选型理由

| 领域 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.10 | AI 生态最成熟，团队通用 |
| Web 框架 | FastAPI | 类型校验、自动文档、异步支持好 |
| 数据校验 | Pydantic v2 | 同一套模型既做接口校验也做配置校验 |
| 数据库 | SQLite（WAL 模式） | 单机零运维、事务完整；演示与中小规模足够；后续可平滑迁 PostgreSQL |
| 向量检索 | sqlite-vec | 与主库同文件、零额外服务；接口已抽象，可换 Milvus |
| 大模型 | DeepSeek（OpenAI 兼容接口） | 中文能力强、成本低；兼容协议意味着可随时换供应商 |
| 文本嵌入 | 本地 Ollama + bge-m3 | 1024 维、中文效果好、不出网、无调用费用 |
| 文档解析 | pypdf | 轻量、纯 Python，处理文本型 PDF 足够 |
| 任务队列 | SQLite 表 + 可见性锁 | 不引入 Redis/Celery，减少部署依赖；语义清晰可控 |
| 前端 | 单文件 HTML + 原生 JS | 无构建、无 CDN，双击即用，方便演示 |

**关于不引入 LangChain**：流程只有五步且顺序固定，直接写编排更可读、更好测，也避免了框架升级带来的不确定性。

## 5. 系统架构

### 5.1 分层

```
接口层（HTTP）
    ↓
编排层（流程顺序）
    ↓
业务规则层（纯计算、纯判断）      ← 不依赖任何框架
    ↑
实现层（数据库 / 大模型 / 向量库 / PDF / 队列）
```

另有一层"接口定义"，规定每一类外部能力需要提供哪些方法；实现层按契约提供具体实现，编排层只依赖契约、不依赖具体实现。

### 5.2 依赖方向为什么重要

| 规则 | 违反后的后果 |
|---|---|
| 业务规则层不引用框架和数据库 | 想测"本科够不够格"得先搭一套数据库 |
| 编排层只依赖接口、不认识具体实现 | 换模型或换向量库要改业务流程 |
| 实现层不认识业务流程 | 会出现循环依赖，无法独立复用 |
| 只有启动入口负责把接口和实现接线 | 换技术栈要改遍全项目 |

**收益**：换大模型供应商、换向量库、换数据库，都只改启动时的装配，业务代码不动。

### 5.3 进程模型

系统有两个独立进程：

- **Web 进程**：接收请求、读写数据库、创建任务，不做重活；
- **Worker 进程**：循环领取任务，执行解析、抽取、嵌入、评分、写报告。

两者只通过数据库中的任务表通信。好处是 Web 再忙也不会阻塞任务处理，Worker 崩了重启即可继续。

## 6. 核心业务流程

### 6.1 简历入库（写路径）

```
上传 PDF
  → 校验格式与大小
  → 计算内容指纹，判断是否重复
  → 保存原始文件 + 写入"待处理"记录
  → 立即返回（用户不用等）
        ↓ 后台
  → 解析 PDF 得到纯文本
  → 调用大模型抽取结构化字段（姓名、技能、学历、经历、期望薪资等）
  → 把结构化字段拆到多张关联表
  → 生成嵌入向量并写入向量索引
  → 标记为"已入库"
```

状态依次是：排队 → 已解析 → 已抽取 → 已入库；任何一步失败都记录失败原因，可重试。

### 6.2 简历筛选（读路径）

```
输入一句岗位需求
  → 大模型解析成结构化查询条件（学历、技能、经验年限、地点、薪资范围）
  → 创建筛选任务并立即返回
        ↓ 后台
  → 语义召回：向量检索取相似度最高的若干份
  → 硬性过滤：学历、经验、地点、薪资逐项判断
  → 多维评分：六个维度各自打分，再加语义相似度
  → 排序
  → 对前 N 名调用大模型生成评估报告
  → 结果落库
        ↓
  → 前端轮询进度，完成后读取结果
```

### 6.3 评分模型

```
最终分 = 六维加权分 × (1 - 语义权重) + 语义相似度 × 语义权重
```

六个维度：技能、学历、行业、地点、薪资、标签。

- 每个维度输出**分数、权重、理由**三部分，前端可以直接展示"为什么是这个分"。
- 简历里没写的维度**从分母中剔除**，不按 0 分计算。
- 系统提供三套评分档案（技术岗、销售岗、严招），权重不同，切换即可。

## 7. 关键技术实现（面试重点）

> 每一条都是"遇到什么问题 → 用了什么技术 → 达到什么效果"。

### 7.1 异步任务与崩溃恢复

**问题**：解析和模型调用要十几秒，放在 HTTP 请求里会超时、无法并发。

**技术**：基于数据库表实现的任务队列。领取任务时不是直接删除，而是给任务加一个"锁定到某时刻"的时间戳并累加尝试次数；任务完成才标记完成，失败则按可恢复/不可恢复分类处理。

**效果**：

- 提交接口毫秒级返回；
- Worker 崩溃后，锁到期任务自动回到队列，不会丢；
- 永久性错误（文件损坏、参数非法）直接进入死信，不做无意义的重复调用；
- 不引入 Redis、Celery，部署仍然只有一个数据库文件。

### 7.2 幂等：重复执行也不会算错、不会多花钱

**问题**：上述队列模型只能保证"至少执行一次"，任务可能被重复处理。

**技术**：

- 上传去重：用文件内容的 SHA-256 指纹做唯一约束，同一份文件永远只有一条记录；
- 处理后去重：已经完成入库的简历、已经完成的筛选任务，重复触发时直接返回既有结果；
- 筛选幂等键：把"岗位文本 + 评分档案 + 简历库版本"三者做哈希，同样的输入不会重复计算。

**效果**：真实环境中重复点击、网络重试、Worker 重启都不会产生第二份数据或第二次模型调用。

### 7.3 唯一真源与可重建索引

**问题**：原项目简历在内存、向量在向量库，重启后不一致。

**技术**：数据库是唯一真源；向量索引是从真源派生的数据，丢失可以重建。删除简历时，同时清理记录、原始文件、向量，并递增"简历库版本号"。

**效果**：

- 重启不会丢数据；
- 简历库变更后，旧的筛选结果自动失效，新简历不会"消失"在历史结果里；
- 数据损坏时，只需重建索引，不需要恢复业务数据。

### 7.4 语义召回 + 结构化过滤，两条腿走路

**问题**：只靠向量检索，无法精确卡住学历、经验年限；只靠条件过滤，又会漏掉"技能名称不同但实际匹配"的人。

**技术**：

- 语义召回：向量相似度检索，兼顾同义表达；
- 结构化过滤：把技能、地点、学历、工作经历拆成独立的关系表并建索引，用 SQL 完成条件判断。

**关键顺序**：**先召回到较大候选池，再做硬过滤**。如果先截断再过滤，"语义排第 11 名但硬条件完全匹配"的人会被提前丢弃。

### 7.5 策略外置与启动校验

**问题**：权重、召回数量、报告数量散落在代码里，调整策略要改代码、要重新测试。

**技术**：

- 权重、召回数量、报告数量、缺失字段策略全部放在 YAML 配置中；
- 启动时做严格校验：六个维度权重之和必须等于 1，维度名拼错直接报错；
- 提示词模板带版本号，落库时记录本次结果使用的是哪一版。

**效果**：

- 调权重不改代码，改完重启即生效；
- 配置写错在启动时就暴露，而不是线上算错分；
- 发现某一批简历抽取质量差时，能定位到具体提示词版本。

**一个刻意的选择**：权重之和不为 1 时**拒绝启动**，而不是自动归一化。自动修正会让调参的人误以为配置生效了，实际问题被掩盖。

### 7.6 缺失字段的处理

**问题**：简历没写期望薪资，按 0 分算，会让"写得详细但不匹配"的人排在"匹配但没写全"的人前面——分数反映的是简历完整度，不是匹配度。

**技术**：缺失维度从分母中剔除，只对有数据的维度做加权；同时输出"覆盖率"，表示本次评分覆盖了几个维度。

**效果**：评分更接近真实匹配度；代价是当岗位只写了两三个条件时，分数普遍偏高、区分度下降，所以覆盖率必须一起展示给使用者。

### 7.7 大模型的结构化输出

**问题**：大模型返回的是自然语言，格式不稳定，直接解析容易失败。

**技术**：

- 用数据模型约束输出格式，解析失败自动重试；
- 在系统提示词中统一注入当前日期锚点；
- 对"至今"这类相对时间，要求模型原样返回，不在抽取阶段换算成具体月份。

**效果**：抽取成功率稳定；写入数据库的时间统一为 `YYYY-MM` 格式；"至今"在数据库中不落地为具体月份，任何时候查询都能得到正确的经验年限。

### 7.8 可插拔设计

**技术**：每一类外部能力都先定义接口（文档解析、大模型、嵌入、向量存储、数据仓储、任务队列），业务代码只依赖接口。

**效果**：

- 大模型按 OpenAI 兼容协议对接，换供应商基本只改配置；
- 向量库从 SQLite 扩展到 Milvus，业务代码不动；
- 测试时可以注入假实现，不产生真实费用、不依赖网络。

## 10. 两个真实踩坑

> 面试时讲这两段，比讲技术名词更有说服力。

### 10.1 报告凭空判定"时间造假"

报告里出现"候选人工作结束时间晚于当前时间，疑似造假"。

排查结果是：简历原文写的是到 2026 年 9 月，而当时是 2026 年 10 月——那只是上个月。真正的原因是**提示词里没有告诉模型当前日期**，模型只能拿训练数据里的"现在"去推断。

修复方式是在系统级提示词里统一注入日期锚点，而不是每个模板各写一遍；同时约束抽取阶段不要自作主张换算相对时间。

**收获**：大模型不是数据库，它没有"今天"这个概念，涉及时间的任务必须显式喂给它。

### 10.2 端到端验收全军覆没

第一次跑真实链路，三份简历全部被淘汰。原因是样本简历是英文的（写 Beijing），岗位需求是中文的（写"北京"），地点匹配做的是字符串包含判断，交集为空。

这不是代码缺陷，是能力边界：**地点匹配没有中英文归一**。修法是加地名别名表，或者在抽取阶段统一映射到标准城市名。

**收获**：单元测试全绿不代表端到端可用，真实数据的多样性只有跑一遍才知道。

## 11. 已知局限与改进路线

按"上生产前必须先修"排序。

| 优先级 | 局限 | 影响 | 改进方向 |
|---|---|---|---|
| P0 | 没有登录与权限 | 能访问端口的人可以查看全部简历 | 加 API Key / JWT，管理接口单独授权 |
| P0 | 地点匹配是字符串包含 | 中英文、简称与全称互不识别 | 地名别名表，或抽取时统一标准城市名 |
| P1 | 幂等键不含配置版本 | 改了权重但简历库没变时会命中旧结果 | 幂等键加入配置指纹 |
| P1 | 报告串行生成 | 10 份报告约等于 10 倍单次延迟 | 线程池并发，控制在 3–5 并发 |
| P1 | 单 Worker 串行消费 | 批量上传 100 份需要排队 | 多 Worker 进程（队列锁已保证不重复） |
| P2 | 只支持文本型 PDF | 扫描件没有文字层，无法处理 | 接入 OCR |
| P2 | 技能匹配是启发式 | `k8s` 匹配不到 `Kubernetes` | 技能词表 + 别名映射 |
| P2 | 无容器化、无 CI、无数据库迁移 | 换机器部署要手动配环境 | Dockerfile + GitHub Actions + 迁移脚本 |

**面试时的讲法**：不要逐条念。挑 P0 的两条讲，并说明判断依据——简历是个人隐私数据，鉴权是上线前提；地点归一是在端到端验收中实测发现的。

## 13. 常见追问速答

| 问题 | 回答 |
|---|---|
| 为什么不用 LangChain？ | 流程固定只有五步，直接编排更可读、更好测，也避免框架升级风险。 |
| 为什么用 SQLite 做队列？ | 演示和中小规模够用，零额外部署；队列语义（锁定、重试、死信）自己实现，行为完全可控。规模上来后换专业队列即可。 |
| 向量库为什么不用 Chroma / Milvus？ | 当前数据量小，与主库同文件最省事；接口已抽象，换库只改装配。 |
| 大模型成本怎么控制？ | 只对前 N 名生成报告；同一输入命中幂等不重复调用；抽取阶段使用结构化输出减少重试。 |
| 权重怎么调？ | 改 YAML，重启生效；权重和必须为 1，否则拒绝启动。 |
| 如何处理模型幻觉？ | 抽取结果全部经过结构化模型校验；报告只基于已抽取字段生成；关键字段保留原文供人工核对。 |
| 系统最大的技术风险是什么？ | SQLite 单写者 + 单 Worker。演示规模完全够用，并发上传时队列会成为瓶颈，扩展方式是换数据库、多 Worker。 |
| 如果简历量到十万份怎么办？ | 数据库迁 PostgreSQL，向量迁 Milvus，队列换专业组件，Worker 横向扩展；业务流程不需要改。 |
