# 智能简历筛选系统

> 上传简历、写一句岗位需求，自动完成解析、语义召回、硬性过滤、多维评分与报告生成。

一个面向招聘场景的后端服务。HR 不再需要逐份翻阅简历，也不必为每位候选人手写评价——系统把"一百份简历看三个多小时"压缩成三步操作：上传、描述岗位、看排序。

## 解决什么问题

| 痛点 | 具体表现 |
|---|---|
| 耗时 | 单份简历人工阅读约 2 分钟，100 份约 3 小时 |
| 标准不一 | 不同人关注的维度、权重不同，结果不可复现 |
| 只看关键词 | 人工检索容易漏掉"技能名称不同但能力相同"的候选人 |
| 写评价费时 | 通过初筛的候选人还要逐份写推荐理由 |

系统对前三项给出统一的、可复现的排序结果，对第四项自动生成评估报告。

## 核心流程

一条五步漏斗，先宽后窄：

```
                    ┌─────────────────────────────────────┐
   简历入库          │  PDF → 抽文本 → 大模型抽取 → 落库 → 向量化 │
                    └─────────────────────────────────────┘
                                      ↓
   岗位筛选    一句话需求 → 语义召回(100) → 硬过滤 → 六维评分 → 排序 → Top-N 报告
                              ↑ 宽              ↑ 窄                        ↑ 最贵
```

**为什么先召回再过滤，而不是反过来**：硬性条件只有学历、经验、地点几项，符合的人可能有几百个；而语义相似度能从全量里捞出"看起来像"的候选人。若先按 `top_k` 截断再过滤，第 11 名那位恰好符合条件的候选人会在进入学历检查之前就被丢弃——没有任何一步看过他。

**为什么报告只给前几名**：生成报告需要逐人调用大模型，是全流程最贵的一步。第 11 名之后的报告没人会点开。

## 技术栈

| 领域 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.10 | AI 生态成熟 |
| Web 框架 | FastAPI | 类型校验、自动文档 |
| 数据校验 | Pydantic v2 | 同一套模型既做接口校验也做配置校验 |
| 数据库 | SQLite（WAL 模式） | 单机零运维、事务完整，可平滑迁 PostgreSQL |
| 向量检索 | sqlite-vec | 与主库同文件、零额外服务 |
| 大模型 | DeepSeek（OpenAI 兼容） | 中文能力强、可随时换供应商 |
| 文本嵌入 | 本地 Ollama + bge-m3 | 1024 维、不出网、无调用费用 |
| 文档解析 | pypdf | 纯 Python，处理文本型 PDF 足够 |
| 任务队列 | SQLite 表 + 可见性锁 | 不引入 Redis/Celery，少一个部署依赖 |
| 前端 | 单文件 HTML + 原生 JS | 无构建、无 CDN |

**不引入 LangChain / LangGraph**：流程固定为五步、没有运行时分支决策，直接写编排更可读、更好测，也避免框架升级带来的不确定性。若将来需要动态决策（召回不足时自动放宽条件重试、人工审核后继续），那才是引入工作流框架的时机。

## 架构设计

### 分层

```
HTTP 接口层   api/
     ↓        只做参数校验、调服务、返回
流程编排层   services/
     ↓        决定"先做什么、再做什么"
接口定义层   ports/        用 Protocol 声明需要什么能力
     ↑
具体实现层   adapters/     数据库、大模型、向量库、PDF、队列
     ↑
业务规则层   domain/       评分、过滤、日期解析 —— 零框架依赖
```

**依赖只能单向流动**：`domain` 不 import 任何 adapter、FastAPI、数据库驱动或大模型 SDK。只有组合根（`main.py` / `worker.py` / `deps.py`）才知道具体实现是谁。

代价是文件数变多；收益是**最难的业务规则可以脱离网络和数据库做纯函数测试**——448 个测试 12 秒跑完。

### 五条核心设计决策

| 决策 | 做法 | 解决了什么 |
|---|---|---|
| **真源唯一** | SQLite 是唯一真源，向量索引、任务队列都是可重建的派生数据 | 避免"简历在内存、向量在另一处，重启后对不上" |
| **写操作异步化** | `POST` 入队即返回 202，独立 worker 进程消费 | 避免请求阻塞几十秒、连接超时 |
| **幂等优先** | 上传靠内容哈希去重，筛选靠 `sha256(岗位+档案+语料版本)` | 重复执行无害，网络重发/连点两次不会多花钱 |
| **策略外置** | 权重、召回数、报告数在 `config/scoring.yaml`，权重和不为 1 则拒绝启动 | 调策略不改代码，也不静默修正让人误以为生效 |
| **评分带过程** | 每维度返回 `(分数, 权重, 理由)`，缺失维度从分母剔除 | 能解释"为什么推荐这个人"，且不惩罚简历写得简略的人 |

### 异常与重试

错误按"值不值得再试一次"分类：

- **文档解析错误** → 不重试，直接进死信（文件坏了，重试结果一样）
- **大模型 / 嵌入错误** → 重试（网络抖动、服务未启动）
- **参数 / 类型错误** → 不重试（代码 bug）
- **未知异常** → 保守重试，靠 3 次上限兜底

任务领取时即 `attempts + 1`，即使 worker 领完就崩溃也会计数。超限进入 `dead` 状态并保留记录，不会无限重试。

单个候选人报告失败不影响其他候选人，整次筛选标记为 `partial` 而非 `failed`——错误不该传染。

## 快速开始

### 前置条件

- Python 3.10+
- [Ollama](https://ollama.com/) 本地运行，且已拉取嵌入模型：`ollama pull bge-m3`
- 一个 OpenAI 兼容的大模型 API（默认配置为 DeepSeek）

### 1. 安装依赖

```bash
pip install -r requirements.txt
```

### 2. 配置环境变量

```bash
cp .env.example .env
```

然后编辑 `.env`，填入你的 `LLM_API_KEY`。

> `.env` 已被 `.gitignore` 忽略，**永远不会提交**。仓库里只有不含真实值的 `.env.example`。

关键变量：

| 变量 | 说明 |
|---|---|
| `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` | 大模型配置 |
| `EMBEDDING_BASE_URL` | Ollama 地址，**必须是 `http://`**，写 https 会连接失败 |
| `EMBEDDING_MODEL` / `EMBEDDING_DIMENSIONS` | 默认 `bge-m3` / `1024` |
| `DB_PATH` / `BLOB_DIR` | 数据库与原始文件目录，默认 `data/` |

### 3. 启动服务

```bash
python scripts/dev.py          # 同时启动 API(8000) 与 worker
```

或分两个终端手动启动（推荐，便于单独看日志）：

```bash
python -m uvicorn app.main:app --port 8000    # 终端 1：API
python -m app.worker                          # 终端 2：后台任务
```

打开 <http://127.0.0.1:8000/> 即可使用内置演示页。

> **必须是两个进程**。worker 崩溃时 API 仍能接收上传、查询状态；API 崩溃时正在跑的任务仍在队列里，锁过期后会被重新领取。

### 4. 跑通全链路（可选）

```bash
python scripts/make_samples.py    # 生成 3 份测试简历 PDF
python scripts/smoke_test.py      # 端到端验收（真实调用 LLM，约 7 次）
```

### 5. 跑测试

```bash
python -m pytest tests/ -q        # 448 passed，约 12 秒
```

> 注意用 `python -m pytest` 而不是 `pytest`——项目靠当前工作目录解析包路径，直接调用 `pytest` 会导致 import 失败。

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/resumes` | 上传简历（支持多文件），`202` 入队 |
| `GET` | `/api/v1/resumes` | 简历列表与处理状态 |
| `GET` | `/api/v1/resumes/{id}` | 简历详情与结构化元数据 |
| `DELETE` | `/api/v1/resumes/{id}` | 删除单份简历 |
| `DELETE` | `/api/v1/resumes` | 清空全部简历（演示用） |
| `POST` | `/api/v1/runs` | 提交筛选任务，`202` 入队 |
| `GET` | `/api/v1/runs/{id}` | 查询进度与摘要（**纯读，无副作用**） |
| `GET` | `/api/v1/runs/{id}/results` | 完整结果与报告 |
| `GET` | `/api/v1/health` | 健康检查 |
| `GET` | `/api/v1/profiles` | 可用评分档案与权重 |

交互式文档：服务启动后访问 <http://127.0.0.1:8000/docs>。

**核心约定**：所有写操作返回 `202` + 任务 ID，所有查询接口都是纯读。查询重复执行不会触发任何计算或费用。

## 实测结果

3 份简历走完整链路（DeepSeek + Ollama bge-m3）：

```
上传 3 份  →  全部 indexed（约 25 秒）
提交「招 Python 后端工程师，本科及以上，3 年以上工作经验」
          →  succeeded
             recall=3 / 过滤后通过=2 / 评分=3 / 生成报告=2

张三 0.920  ✅ 通过，附评估报告
王五 0.916  ✅ 通过，附评估报告
李四 ——     ❌ 淘汰，原因保留：大专低于本科要求
```

同一 query 再次提交 → `deduplicated=true`，**零额外 LLM 调用**。

| 指标 | 数值 |
|---|---|
| 代码量 | 约 5400 行（不含测试） |
| 数据表 | 11 张 |
| API 接口 | 10 个 |
| 自动化测试 | 448 个，约 12 秒 |

## 已知限制

诚实记录，避免误用：

**P0 — 上线前必须解决**
- 无认证与权限：任何能访问端口的人都能查看、删除全部简历
- 数据未加密：简历含姓名、电话、邮箱等个人信息
- 原始文件存本地目录，未使用对象存储

**P1 — 规模化前必须解决**
- SQLite 单写者：并发写会排队，多机部署需替换为 PostgreSQL（仓储层已抽象，仅需重写一个 adapter）
- 无数据库迁移机制：表结构变更缺少可回滚的迁移脚本
- 单 worker 进程：任务串行处理
- 死信无告警、无重放接口

**P2 — 质量与可观测性**
- **检索效果无量化指标**：目前只能人工判断筛选结果是否合理，缺少标注测试集中的召回率/准确率。所有参数调整缺乏客观依据——这是本项目最大的短板
- 无结构化日志、指标采集、链路追踪
- `/health` 只检查数据库，不检查 LLM 与嵌入服务（刻意为之：健康探测频率高，真实调用会产生费用）
- 地点硬过滤为字符串匹配，多语言简历（如 `Beijing` vs `北京`）会误杀
